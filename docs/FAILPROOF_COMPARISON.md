# Failproof comparison: three controlled failure cases

**Date:** 25 September 2026

**Scope:** Offline SDK component comparison with scripted policies and synthetic state.

## Result and decision

Both implementations detected all three seeded unsafe runs, passed all nine
safe controls, and identified the first offending refund effect. This experiment
shows no detection advantage for Agent Action Evals.

The useful distinction in this implementation is fixture and fault authoring.
Agent Action Evals already provides world reset, deterministic tool faults, and
state assertions. For Failproof, we supplied a custom simulator and authoritative
state telemetry, then evaluated it with custom checks in its actual SDK worker.

**Decision:** focus Agent Action Evals on reusable fault-injection fixtures for
agent regression tests. It can complement an evaluation platform such as
Failproof. Lower integration effort is a hypothesis to validate with external
teams; this experiment alone does not establish a product advantage.

## What actually ran

- **Agent Action Evals:** the existing `run_scenario`, SQLite world, fault
  controller, and state/count/precondition assertions.
- **Failproof:** SDK version `0.0.1b5` from commit
  [`b8cce3b221f94b74b7283a6df63ffb603712776a`](https://github.com/FailproofAI/failproofai/tree/b8cce3b221f94b74b7283a6df63ffb603712776a).
  Its `WorkerRuntime.process_assignment` selected and invoked our custom
  evaluator, validated its typed results, and submitted them to a memory
  transport. Only the server transport was substituted.
- **Shared inputs:** the same Python policy and tool handler implementations,
  initial state, expected contract, fault schedule, and independently defined
  labels. Each backend executed the agent in its own fresh simulator.
- **Evidence parity:** all twelve executions had identical tool-call sequences,
  tool observations, and final state between the two backends. Failproof received
  before/after state snapshots and execution markers as custom audit payloads.

The Failproof path did not consume AAE verdicts, findings, precondition-failure
markers, or mutation labels. Both evaluators received the expected contract;
neither agent received it.

No live model, hosted Failproof service, ingestion pipeline, dashboard, cloud
worker scheduling, automatic tracing adapter, audit, or runtime policy was
exercised. Those capabilities are outside this component comparison. Missing
cloud credentials are not counted as failures.

## Cases and measurements

Each family has a base fixture and one changed fixture, run with a reference
policy and a deliberately faulty policy. All six base runs are safe; the three
changed/reference runs are safe; the three changed/mutant runs are unsafe.

| Family | Changed fixture or fault | Mutant behavior | AAE | Failproof SDK + custom check |
| --- | --- | --- | --- | --- |
| Lost response | First refund commits, then its response is lost | Retries without reading state, creating a second refund | Detected | Detected |
| Stale read | First lookup hides an existing refund | Skips the fresh lookup and refunds again | Detected | Detected |
| Ownership | Caller differs from the order owner | Ignores the ownership mismatch and refunds | Detected | Detected |

| Measurement | AAE | Failproof SDK + custom check |
| --- | --- | --- |
| Unsafe runs detected | 3/3 | 3/3 |
| Safe controls passed | 9/9 | 9/9 |
| False alarms | 0 | 0 |
| Scored-case execution errors | 0 | 0 |
| First offending effect identified | 3/3 | 3/3 |

Failproof's explanation contains event IDs selected by our custom check. AAE's
findings contain event references generated by its existing assertion engine.
This is event attribution based on observable effects, without a claim about
why a model made its decision. No human study of explanation quality was run.

An additional control removes the final authoritative state from a Failproof
transcript. Our check raises an error; the SDK records `eval_error`. This verifies
our check's handling of missing evidence. It does not imply that every Failproof
evaluation has that behavior by default.

See the [complete machine-readable results](../benchmarks/results/failproof-comparison.json)
for both event histories, verdicts, source hashes, upstream revision, and control
results. Run the [reproduction commands](../benchmarks/comparison/README.md).

## Setup work observed

The implementation required the following source, counted as nonblank lines
that do not begin with a Python comment. Docstrings and imports are included.

| Authored component | Lines | Role |
| --- | --- | --- |
| Shared cases, policies, handlers | 84 | Used by both paths |
| AAE integration | 54 | Driver, declarative fixture/fault configuration, assertions |
| Failproof custom simulator | 73 | State reset, faults, effect telemetry |
| Failproof custom checks | 49 | Outcome, counts, preconditions, event references |
| Failproof local transport adapter | 96 | Offline benchmark infrastructure; replaces the server |
| Comparison runner | 224 | Provenance, parity checks, scoring, export |

The 96-line transport adapter exists to make this experiment runnable without a
Failproof account; it is not a requirement for a normal hosted deployment. The
simulator is intentionally small and supports only this corpus. These counts
exclude each product's existing library code and do not measure developer time,
maintenance cost, or integration with an existing production test environment.
We did not run a controlled, independent developer-effort study.

What remains promising is packaging reusable failure simulations. A team that
already has a simulator and state telemetry may obtain little additional value
from our framework. A team starting from plain tool functions may benefit more.

## How this fits Failproof's existing capabilities

Failproof documents deterministic Python evaluations and custom worker checks
through its [Evaluator SDK](https://docs.befailproof.ai/reference/evaluator-sdk).
The experiment confirms that its SDK can express the outcome checks used here
when supplied with the required evidence.

Its broader workflow includes session tracing, audits, policy testing, and live
enforcement. Those are described in its
[repository](https://github.com/FailproofAI/failproofai) and
[documentation index](https://docs.befailproof.ai/llms.txt). We did not find a
built-in stateful fault-injection runner in the reviewed SDK/docs. This is a
bounded documentation finding, not proof that Failproof cannot support such a
workflow or that no other product already does.

## Next validation gate

Before broadening the framework, ask two external teams to reproduce one real
incident each using their own agents and existing eval stack. Measure:

1. Active time and code changes needed to bind tools and author the scenario.
2. Whether state and effect evidence survive ambiguous responses correctly.
3. Whether the report makes the offending effect clear to another developer.
4. Whether the test remains useful after a prompt, model, or tool change.

If reusable simulation does not reduce meaningful work, prefer an adapter or
contribution to an existing project. No monitoring dashboard, general LLM judge
platform, or runtime enforcement expansion is justified by these results.
